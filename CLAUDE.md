# Smahbros

Smash Bros tournament bracket platform.

## Architecture

| Layer | Tech | Deploy |
|---|---|---|
| Backend API | FastAPI (Python) | Render — `smash-bracket-api.onrender.com` |
| Frontend | Next.js 16 / React 19 (migration in progress) over legacy Vanilla HTML/CSS/JS | Vercel — `bracket-self.vercel.app` |
| Database | SQLAlchemy → SQLite (local) / PostgreSQL (prod) | Supabase |
| Assets | Fighter images | Supabase Storage bucket `Characters` |

`web/app/*` is the Next.js frontend, fully migrated *to* — all 14 legacy pages have React ports. `web/public/*` is the legacy vanilla frontend migrated *from*; its `.html` pages are now archive-only, not a live parallel surface: `next.config.js`'s `redirects()` intercepts every old path (e.g. `/duel.html`) before Next's filesystem routing would otherwise serve the static file, sending visitors straight to the React route instead. The files themselves are untouched on disk and in git — readable for reference — but unreachable **by URL**, including by a developer typing the old path to compare legacy behavior against a React port side-by-side (the verification method used throughout the migration). `web/public/js/*` (`api.js`, `auth.js`, `nav-inject.js`, `game-menu.js`) are similarly inert now — no `web/app/*` page loads them at runtime, confirmed by grep; they exist only for the archived pages that reference them.

## Key Files

```
api.py              — FastAPI app, lifespan startup, _run_migrations(), WebSocket routes
database.py         — All SQLAlchemy models (User, Bracket, TournamentInvite, Match, …)
ws_manager.py       — WebSocket room manager for live tournament + draft-room pushes
                       (routers/draft.py's ws_manager.push, /ws/tournament/{id} in api.py)
auth.py             — JWT helpers (HS256, token in localStorage.authToken)
routers/            — One file per resource (auth, brackets, matches, friends, …)
web/app/lib/api.ts  — Canonical API client for the Next.js app — typed port of web/public/js/api.js
web/app/lib/gameMenu.tsx — Cinematic-menu content (summary types, PanelContent/PosterCard,
                       SECONDARY items, summary fetch+cache) shared by page.tsx's inline
                       menu and GameMenuOverlay.tsx's dialog — edit here, not in either caller
web/public/js/auth.js      — requireAuth() guard — must be first script on every legacy page
web/public/js/api.js       — API_BASE constant + fetch wrappers — never hardcode the URL
web/public/js/nav-inject.js — Injects shared nav bar — never hardcode nav HTML in legacy pages
```

## Conventions

**Frontend**
- Legacy (`web/public/*`) pages: every page loads `<script src="js/auth.js"></script>` then immediately `<script>requireAuth();</script>`; all API calls go through `API_BASE` from `api.js`; nav injected by `nav-inject.js` — no duplicate nav markup; no build step, plain ES5-compatible JS, no imports.
- `requireAuth()` is the legacy pattern — it's still correct and required on every un-migrated page, but new Next.js pages get their own React auth-guard equivalent instead (planned, not yet built) rather than porting `requireAuth()` literally.
- All API calls from `web/app/*` go through `web/app/lib/api.ts`, not a reimplementation.

**Backend**
- New DB columns: add `ADD COLUMN IF NOT EXISTS` in `_run_migrations()`, not a new Alembic file
- All routes return JSON; errors use `JSONResponse(status_code=…)`
- Auth middleware extracts JWT via `decode_token()` from `auth.py`
- Rate limiting lives in `routers/ratelimit.py`

## Gotchas

- Render cold-starts take **~30 s** — lobby shows a "server waking up" message after 4 s
- PostgreSQL prod URL starts `postgres://` but SQLAlchemy needs `postgresql://` — patched in `database.py`
- `smash.db` (SQLite) is local-only; never commit it
- Supabase image URLs use `%20` encoding for spaces in fighter names (e.g. `Donkey%20Kong.png`)

## Known Gaps

- **Manual "send an invite" flow was specced but never wired up.** `web/public/invites.html`'s JS has complete logic for searching a user and sending them a tournament invite (`searchUsers`/`selectInvitee`/`sendInvite`), but the HTML form those functions target was never added to the page — it's dead code, unreachable from the live UI. Today, invites are only ever created automatically when starting a live tournament from the Bracket page (`POST /invites` is called from there, not from `invites.html`). The Next.js port (`web/app/invites`) intentionally dropped the dead JS rather than porting unreachable code or building the missing UI. Decide separately whether a manual send flow is actually wanted — with a small group already in the same room, the automatic path from Bracket may be the only one that's ever needed, in which case dropping it was permanent, not just deferred.
- **Duels have no actual series-end.** `web/public/duel.html` has "Series Winner" banner markup and a `seriesWinner` guard, but nothing in the file ever sets `seriesWinner` truthy — a duel is really just an open-ended running score (`p1Score`/`p2Score` tallied per recorded game) with a manual "New Series" reset, not a best-of-N that concludes on its own. The Next.js port (`web/app/duel`) reproduces exactly that: no series-end detection, no winner banner. This is a real feature decision waiting, not lost knowledge — and it's bigger than "add first-to-3 logic" once it comes up: 2-player draft rooms may end up routed into the duel flow as a series (chars-per-player is already 1/4/8 there), in which case series length should come from the draft, not be hardcoded on the duel page. Decide once that shape is clearer.
- **`POST /matches/record` 403s for every non-admin user whenever the call isn't tied to a live bracket — confirmed live on both Duel and (manual) Bracket, not theoretical.** `routers/matches.py:154` requires either `current_user.is_admin` or a `bracket_id` tied to a bracket the caller hosts. `web/public/duel.html`'s `recordGame()` never sends `bracket_id` at all (a 1v1 duel isn't tied to any bracket), so clicking a score button there only works for admins. **Correction to this entry's original scope claim** ("bracket.html... correctly pass bracket_id"): that's only true *after* a live tournament has been started from that page — `bracket.html`'s `recordMatchResult()` sends `bracket_id: liveTournamentId || null`, and `liveTournamentId` stays `null` for the page's default, more common flow (build a bracket manually, score it via the VS modal or winner-select dropdown, only start it live afterward if at all). Reproduced live during the Next.js bracket-page port: generated a 2-player manual bracket as a fresh non-admin user, scored all 3 matches (R1 ×2 + Grand Final) through the VS modal, all 3 `/matches/record` calls 403'd — round winners/scores/Elo-preview/connector-lines/champion-banner all still worked client-side (the call is wrapped in try/catch, same as Duel), but no Elo/kills/wins were actually saved server-side. `tournament.html` is unaffected — every match there is inherently tied to an already-live bracket, so `bracket_id` is always real. The Next.js ports (`web/app/duel`, `web/app/bracket`) both reproduce the exact same calls (still 403 for non-admins in the same conditions) rather than fixing inline — fix as its own task, and when it lands, fix both call sites (Duel's missing `bracket_id` entirely, and Bracket's `null` case for not-yet-live brackets) together since they're the same root cause.
- **User-average leaderboard's weighted/simple toggle was never wired up.** `web/public/leaderboard.html` has a `setAvgMode('weighted'|'simple')` function and CSS for `.avg-toggle-btns`, but no actual `<button>` elements exist anywhere in the HTML to call it — `avgMode` is permanently stuck at `'weighted'`. The Next.js port (`web/app/leaderboard`) always renders the weighted average and drops the dead toggle function, matching what's actually reachable today.
- **`tournament.html`'s VS score modal has a detail panel (`#desktopScoreGrid` — the per-scenario rank-arrow + Elo table with `score-preset-btn` buttons) that is dead in every viewport, not just desktop despite the name.** It starts `display:none` inline and nothing ever un-hides it: on desktop/landscape there's no CSS rule overriding the inline style, and on portrait mobile `style.css`'s `@media (max-width: 600px) and (orientation: portrait)` block explicitly forces it `display:none !important` too (that same block is what shows its sibling, `#mobileScorePicker`, the winner-first card picker — which *is* live, on portrait phones only). So on desktop, scoring only ever happens through the compact `.vcp-btn` 3-0/3-1/3-2 buttons in the center panel (with hover Elo preview) — the detailed grid was never reachable. The Next.js port (`web/app/tournament`) drops `#desktopScoreGrid`'s markup entirely and keeps only the compact center-panel buttons (desktop) + `#mobileScorePicker` (portrait mobile, same id so the existing media-query CSS keeps applying unchanged). Decide separately whether desktop should actually get a detailed rank/Elo grid — if so it needs real show/hide CSS, not just porting the dead markup as-is.
- **`bracket.html`'s entry-grid character auto-fill has never actually worked.** `buildEntryGrid()`/`getEntryPoints()`/the Save-Preset default-population code all read `document.querySelector('input[name="fillMode"]:checked')` to decide whether to auto-fill each player's characters by Elo/Kills/Win%/Favorites/Tier-list — but no `<input name="fillMode">` radio group exists anywhere in the page's HTML (unlike `bracketStyle`/`seedMode`, which really are rendered by `bracket-options.js`'s `renderBracketOptions()`). The query always returns `undefined`, so `fillMode` always falls back to each call site's own default — `'points'` in `buildEntryGrid()`, which matches none of the real branches — so every character picker in the entry grid starts empty; players have always had to hand-pick every character. `getEntryPoints()` is fully dead code, never called from anywhere. The Next.js port (`web/app/bracket`) reproduces this: entry grid ports as manual-pick-only, `getEntryPoints()` is dropped. Decide separately whether a real fill-mode selector is worth building — the 5 branches (elo/kills/winpct/favorites/tierlist) it would drive already exist and work, they've just never had a control wired to them.
- **No service worker / offline support exists, and never has.** The legacy site's "PWA" support was always just installability (`manifest.json` + the standard `apple-mobile-web-app-*`/`theme-color`/`viewport` meta tags, byte-identical across all 14 pages) — confirmed via a repo-wide grep for `serviceWorker`/`sw.js`/`workbox`/`ServiceWorkerRegistration`, all empty, and no `sw.js` or worker file anywhere. Phase 3 of the Next.js migration ported the installability layer only (`web/app/manifest.ts` + `layout.tsx`'s `metadata`/`viewport` exports) — deliberately did **not** add a service worker, since that would be new functionality, not a port. Building one is a real feature decision waiting: needs a caching strategy design (what to cache, how live WebSocket-driven bracket/duel/draft state avoids being served stale from cache) before any code gets written — not something to bolt on casually given how much of this app is live data.
- **Per-page `<title>` is set client-side via a `useEffect` hook (`web/app/lib/useDocumentTitle.ts`), not real server-rendered metadata, for 13 of the 14 ported pages.** Every `web/app/*/page.tsx` except `play/page.tsx` is a `'use client'` component (data-fetching, WebSocket state, or interactive UI throughout), so none of them can export the server-only `metadata` object Next.js otherwise uses for per-route `<title>` tags — `play/page.tsx` is the one page with no client state, so it gets a real `export const metadata` instead. The hook is a client-side patch, not a complete fix, and it needs a `MutationObserver`, not just a plain `document.title = ...`, to actually work: confirmed live that Next 16 re-renders its own client-side `<title>` element (part of its streaming-metadata machinery) roughly 100ms after mount — even on a statically-prerendered route — which silently overwrites a plain assignment back to the generic root-layout title. Without the observer re-asserting after that happens, every route's tab title reverted to `Smash Bracket` in practice, not just during the brief pre-effect window; this reproduced on every page tested, not as a rare edge case. Two limitations remain even with the observer: the title still isn't set until after first paint (a client-side route change briefly flashes the previous page's title before the effect fires), and anything reading the rendered HTML without executing JS (link-preview unfurlers, some browser-history/bookmark capture paths) still sees the generic root-layout title for all 13 of those routes. The real fix is a thin server-component wrapper per route that exports `metadata`, with the client page nested inside it as a child — real work, deferred rather than done as part of the Phase 4 polish pass that added the hook.

- **Elo and W/L/kills/deaths are stored, mutated-in-place columns — not derived from the match log on read.** `User.elo` and `CharacterStats.{elo,wins,losses,kills,deaths}` are incremented directly in `routers/matches.py::record_match` on every match (`ws.elo = (ws.elo or ELO_DEFAULT) + delta`, etc.) and persisted as-is; nothing recomputes them from `MatchResult` rows at read time. The provisional-games gate (`routers/characters.py`'s `PROVISIONAL_GAMES` check) reads the stored `wins + losses` columns for the same reason. This matters because it means **any bug that ever let a bad match affect these columns is permanent until someone runs a one-off recompute** — fixing the code stops new contamination but does nothing for numbers already written. This surfaced concretely investigating self-match Elo contamination (see the entry below): `record_match`'s `winner.id == loser.id` guard has existed since the very first commit that created the file, so any contaminated numbers predate it or came from a different, no-longer-present code path — not a live bug in the current guard.
- **Free-pool draft brackets can pit two of the same real player's entries against each other from the quarterfinals on — by design (see `_deal_bracket` in `routers/draft.py`), and this used to leave the match completely unlogged.** `routers/matches.py::record_match`'s `winner.id == loser.id` early return used to skip creating a `MatchResult` row at all, not just skip Elo/stats — so a self-match left zero trace in match history, even though the bracket still recorded a winner via the separate `PATCH /brackets/{id}/winner` call. Fixed to still write a `MatchResult` row (`elo_delta=0`, new explicit `is_self_match` column) while leaving every `CharacterStats`/`User` counter untouched, and to exclude self-matches from `/matches/shame` (a self 3-stock isn't a shame-feed moment). The `is_self_match` column is intentionally explicit rather than inferring "was this a self-match" from `winner_id == loser_id` at read time in every future consumer (leaderboard, history, shame feed) — one fact, stored once, not re-derived and potentially gotten wrong independently in each place that cares. `tournament.html`'s VS modal (`web/app/tournament/page.tsx`'s `ScoreModal`) also had its own frontend-side skip (`if (winnerEntry.player !== loserEntry.player)`) that bypassed the `/matches/record` call entirely for a self-match — removed, since the backend guard is meant to be the single place this is decided, not duplicated per call site. The modal now shows "Advance `<character>`" buttons with no Elo preview or rank arrows for a detected self-match, instead of two identical "`<player>` WINS" columns. **Whether historical self-matches already contaminated stored Elo (the trigger for this whole investigation: leap's Joker and R.O.B. character stats were flagged as suspect) is unresolved — needs a `SELECT ... FROM match_results WHERE winner_id = loser_id` sweep run against the real production DB, which no session has had access to yet.**

- **Placement bonuses (1st/2nd/3rd Elo, `Bracket.placements`) used to only ever get computed in `PATCH /brackets/{id}/end` — a separate, host-triggered action from the `PATCH /brackets/{id}/winner` call that actually sets `Bracket.winner` when the Grand Final resolves.** The only "automatic" path was a fragile client-side 30-second undo-timeout in `tournament/page.tsx` that auto-calls `endTournamentNow()` if the just-decided match was the Grand Final and the undo window closes unused — which only fires if that same tab stays open 30 more seconds and nobody uses Undo. Found live via Bracket 91 (Draft #9): `winner = 'kai'`, `placements = NULL` — the isGrandFinal fix (see the entries above) was working correctly, but nothing had computed placements for it. Fixed by extracting the placement/bonus computation into a shared `_award_placements()` (`routers/brackets.py`) and calling it from `set_bracket_winner` the instant `tournament_winner` is set, server-side, with no dependency on any client staying connected. `end_tournament` still calls it too (for an early-end where the Grand Final happens to have just completed, and as a backstop for any bracket whose winner got set some other way) — `_award_placements` is idempotent via `_has_real_placements` (checks for actual `1st`/`2nd`/`3rd` entries, not just a non-null `{}`, since `end_tournament` sets `{}` on *any* end including a genuinely-early one), so calling it from both places can't double-apply the same Elo bonus. **Does not handle correcting a Grand Final result after placements are already set** — that would need to reverse the old bonus before applying a new one, which neither this nor the pre-existing code ever did; a real gap if it comes up, not silently fixed here. **This only applies going forward** — brackets already stuck in the winner-set-but-unplaced state from before this landed (Bracket 91, and Bracket 20 found the same way) still need `scripts/backfill_grand_final_placements.py` run against production; it was widened this same session to catch this exact state (previously it only looked for `winner IS NULL`, which is why it silently missed Bracket 91 the first time), and now has a real `--apply` write path (default stays dry-run).
- **A placement row's displayed timestamp used to be `Bracket.created_at` (when the bracket was *started*), not when the award actually happened — sorted every placement row into the wrong spot in `routers/matches.py`'s `char_elo_history` for any tournament that ran a while.** Confirmed live: Draft #9 (created 12:49 AM) and bracket 4 both showed their placement row above all four of the real matches that earned it, because the last of those matches ran at 6:59 PM, hours after creation. Fixed with a real `Bracket.placements_awarded_at` column, set by `_award_placements` itself the moment it actually writes placements — `char_elo_history` now sorts on that, falling back to `created_at` only for rows placed before the column existed (no better answer available for those, e.g. bracket 21's April placements). The backfill script sets it explicitly to one second after each bracket's own last recorded `MatchResult`, not "now" (the backfill run's own time). **Checked, not assumed, whether the live (non-backfill) path has the same problem: it does, at a much smaller scale.** `_award_placements` runs inside `PATCH /brackets/{id}/winner`, which the frontend (`tournament/page.tsx`'s `pickTournamentScore`, `bracket/page.tsx`'s `setWinner`) calls *before* `POST /matches/record` — so by the time `_award_placements` stamps `placements_awarded_at`, the Grand Final's own `MatchResult` row doesn't exist yet. Measured live: the placement lands ~12ms *before* its own final match's `created_at`, not after. **Decided not to fix**: reordering those two frontend calls (record the match first, then patch the winner) touches the whole scoring flow — Elo award, winner-set, placements, and now the `is_live` auto-clear all live on that call order — to fix an inversion nothing displays at any real granularity; the blast radius is wildly out of proportion to the symptom. Confirmed live (scratch DB, exact real call order reproduced) that `char_elo_history` still renders it correctly regardless: the Grand Final match sorts newest-first as expected, with its placement row immediately beneath it — adjacent and sensible, not swapped or scattered. If this ever does need fixing, the cheap fix is to stamp the live path's `placements_awarded_at` the same way the backfill script already does — one second after the bracket's own last recorded `MatchResult` — instead of `_now()`, rather than reordering the frontend calls. Not worth doing now; recorded here so a future session reaches for that instead of the invasive reorder.
- **Every timestamp the API ever returned was silently wrong once a browser displayed it, on both SQLite and Postgres.** Every `DateTime` column in `database.py` is a plain `Column(DateTime)` (no `timezone=True`), and both backends round-trip it as naive: SQLite always strips tzinfo on read (confirmed live), and Postgres's default `TIMESTAMP WITHOUT TIME ZONE` does the same. `_now()` writes a UTC-aware value, but every value read back is naive again — so all 21 `r.created_at.isoformat()`-style calls across `routers/{brackets,draft,home,characters,invites,matches,presets,users}.py` produced an offset-less ISO string. `web/app/*` already converts every timestamp to the viewer's local time correctly via `new Date(iso).toLocaleString()`/`.toLocaleDateString()` (confirmed — this pattern was already in place everywhere, nothing wrong with the frontend) — but JS's `new Date(...)` parses an *offset-less* ISO string as **local** time, not UTC, so the frontend's own correct local-time conversion was applied on top of an already-mislabeled value, netting out to displaying the server's raw UTC clock as if it were already local. Measured live in a UTC-4 (Detroit) browser: a real API timestamp of `04:15` UTC displayed as `4:15 AM` instead of the correct `12:15 AM` — off by exactly the viewer's offset, every time, every timestamp on the site. Fixed with one shared `to_utc_iso()` (`database.py`, next to `_now()`) that explicitly labels a naive value as UTC before serializing, swapped in at all 21 call sites — no frontend changes needed, since `toLocaleString()` was already correct once given a correctly-labeled input.

## Working Conventions

- **Plan before building, wait for approval.** For anything nontrivial, propose the approach and get a go-ahead before writing code — don't start implementing off an assumed plan.
- **Never commit or push without being asked.** Land changes in the working tree and stop there; committing/pushing is a separate, explicit request every time, not a default step at the end of a task.
- **Don't touch files outside the task's scope.** If something adjacent looks broken or worth improving, mention it — don't fix it inline unless asked.
- **Verify changes rather than assuming they worked.** Spin up the app locally and actually exercise the change (Playwright, curl, or both) before calling something done — don't rely on the code "looking right." If a claimed bug doesn't reproduce, say so plainly instead of making a cosmetic edit to look productive.
- **Ask instead of guessing when a spec is ambiguous.** If the request's own description of current behavior doesn't match what the code actually does, surface that mismatch explicitly rather than silently picking a side.

**Patterns worth keeping in mind, noticed over the course of this repo:**
- Precise, detailed specs are the norm here (ordered pipelines, numbered guard lists, exact reproduction steps) — match that precision, including the edge cases named, not just the headline behavior.
- A recurring class of bug in this codebase is duplicated constants/thresholds drifting apart (provisional-game cutoffs, API base URLs, etc.) — when fixing one instance, it's worth grepping for sibling copies of the same number/logic elsewhere.
- Shared state driving multiple independent surfaces (one checkbox controlling two tables, one endpoint serving two callers with different needs) is a repeat root cause here — prefer decoupling over a shared flag when two consumers' needs might diverge.
- Local verification convention: scratch SQLite DB per feature (`smash_test_<name>.db`), a throwaway `SECRET_KEY`, backend on port 8850 / frontend on 8851, `next.config.js`'s API rewrite and any `WS_ORIGIN`/`API_BASE` constants temporarily pointed at `127.0.0.1:8850` for the test, then reverted to the real production URLs before wrapping up — and the scratch DB and servers torn down (by exact PID, not a name-based kill) at the end.
- Report findings straight — including "this doesn't reproduce" — rather than shaping the story to look done.
